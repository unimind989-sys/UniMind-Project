## S01 — Landing hero and layers

**Structure:** large two-line slogan, explanatory text/CTAs and an animated Open Folio scene; dark sampled in settled evidence, Light explored earlier. **Weakness:** the highly staged metaphor gives more immediate attention to assembly than to how a user obtains an approved unit. **Friction:** role access and the boundaries of the illustrative preview must be inferred. **Cross-screen gap:** the authored folio entry becomes much more ordinary bordered-panel workspaces. **Motion:** assembly 1100 ms/layer 650 ms is a deliberate marketing exception; it should not become an application transition pattern. **Recommendation:** preserve the slogan/brand; add concise approved-material and assigned-access explanation near the CTA; make sample status unmistakable. **Severity/impact:** P3, modest acquisition clarity; application structure has higher priority. Evidence: [desktop](screenshots/p05-landing-desktop.jpg), [mobile](screenshots/p06-landing-mobile.jpg); U41.

## S02 — Interactive public workspace

**Structure:** in-page sample tools reached through Explore workspace, including flip and supplied Quiz. **Weakness:** a visitor can interact but cannot infer the real approval/source/readiness boundary solely from control styling. The existing sample descriptor is useful but does not explain assigned access. **Friction:** demonstration behavior must not imply enabled provider capability. **Cross-screen gap:** the compact demonstration differs from the taller authenticated workflow. **Motion:** flip is meaningful; tool switching should retain the selected region and announce its heading. **Recommendation:** retain the existing sample descriptor, add concise assigned-access context, keep a stable tool canvas and meaningful CTA into account access; reuse authenticated components where practical. **Severity/impact:** P2 clarity, P3 refinement. [Laptop Chat demo](screenshots/p58-public-workspace-laptop.jpg); discovery 3–7 also covers supplied interactions. No invented provider outcome.

## S03 — Sign in

**Structure:** standalone brand/language header, one bordered form, recovery/registration links and educational boundary. **Weakness:** password entry has no visibility toggle; access context is generic despite three different destinations. **Friction:** mobile typing errors are difficult to inspect. **Cross-screen gap:** auth language uses text links; application uses select; these are legitimate surface differences but spacing/action emphasis should share tokens. **Motion:** Working state exists; fixture handoff lazy-load fallback is null in source. **Recommendation:** accessible Show/Hide, stable labelled pending region, short membership-driven access explanation. **Severity/impact:** P2 for first-entry confidence. [Mobile](screenshots/p07-login-mobile-dark.jpg); U28, U29, U31. All four credential pairs were actually entered independently; no role picker was found.

## S04 — Registration validation

**Structure:** email/password/confirmation fields, account-access step indicator, error summary and inline messages. **Weakness:** an empty confirmation produced mismatch wording alongside required errors. **Friction:** summary identifies failure but should navigate directly to corrective fields. **Cross-screen gap:** longer registration uses a narrow auth panel within a wider access composition; hierarchy must separate requirements from submission feedback. **Motion:** Working→error observed; no account creation. **Recommendation:** required-before-mismatch copy, linked field summary with retained values. Existing requirements are already visible before submission. **Severity/impact:** P2; U30. [Initial form](screenshots/p56-register-desktop.jpg), [validation](screenshots/p57-register-validation.jpg), discovery 13–14; partial coverage. No successful registration, verification email or real consent was tested.

## S05 — Recovery

[Tablet](screenshots/p01-recovery-tablet.jpg). No email sent.
