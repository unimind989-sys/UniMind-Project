# Revised delivery plan and acceptance contract

**Proposal only. No implementation approval exists.** The eight-phase structure of the original audit is retained, with shared secondary screens and motion/state proof moved earlier. Estimates are overlapping planning ranges for one experienced frontend engineer, not a quotation. Approximately 18–25 engineering days plus founder review and any separately approved capability work; confidence remains moderate until the approved first slice establishes the shared seams.

## What changes in the roadmap

- Foundations include visual composition, icon geometry, paired surface roles and motion tokens, not just CSS constants.
- Build account/forms/errors/dialogs alongside the first shared components. Otherwise flagship screens improve while ordinary screens retain the old product language.
- Motion is part of component/state acceptance from the beginning. The later motion phase validates continuity and interruption; it does not sprinkle animation onto finished screens.
- Responsive and Arabic checks run in every phase. The final responsive phase tests edge conditions rather than postponing mobile work.
- Keep all 45 original issue IDs. New proposal defects are tracked as refinement risks, not invented live-product defects.
- After approval, select exactly one applicable runbook slice and controlled task record at a time. Preserve WP03-T10’s historical closure. No implementation PR, merge or deployment belongs to the current proposal phase.

## Comparing results fairly

Keep both captures’ role, task, dataset, selection, theme, locale and viewport equivalent. Record unavoidable differences, including scroll origin and the review-only toolbar. Assess visual and task criteria separately. Do not attribute an improvement to newly invented data, a populated output compared with an empty screen, or removed operational context.

Usability validation after approval: ask 5–8 representative students/leaders/staff, with founder-approved recruitment, to complete subject → question → evidence, Studio artifact, source submission/recovery and decision review/cancel tasks. Record unassisted completion, wrong-target choices, corrective backtracking, requests for help and participants’ explanation of source/receipt states. Establish a current-product baseline before claiming improvement in time or error rate. This pass has not conducted that study and authorizes no external messages.

Perceived performance validation: use the same device/network/data for before/after; measure real route/interaction behavior and profile the authored motion. Targets are no new layout shift caused by redesigned controls, no main-thread regression attributable to motion and visible pending feedback before the user repeats an action. Obtain actual LCP/CLS/INP evidence before making metric claims. No measurements of those metrics exist in this proposal.

## Approval boundaries

Approval of the visual direction can authorize a scoped frontend implementation plan. It does not authorize changing authentication, authorization, database rules, durable history, readiness predicates, provider enablement, financial caps or access grants. If any such change becomes necessary, produce a concrete narrow requirement and request explicit approval before that change. Delivery must still follow the selected runbook task’s technical gates.

**Current safe next step:** founder reviews the actual concepts, design system and roadmap and explicitly approves implementation or requests revisions. No deployment follows from merely opening the prototype or saying “continue.”
