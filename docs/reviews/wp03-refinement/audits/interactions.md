# WP03 refinement audit: interactive elements, buttons and input semantics

Audit date: 2026-10-18. Base: `main` at `bcab083`. Method: static read of every `<button>`, `<a>`/`Link`, `<input>`, `<select>`, `<textarea>`, `<dialog>`, `<details>`, `role=`, `onClick`, `onSubmit`, form `action`, `disabled` and `aria-*` under `src/app` (112 `.tsx` files), with handlers traced into hooks, Server Actions and the React/Next runtime where behaviour depended on it. Nothing was rendered: no dev server, build or test run (a `pnpm verify` timing baseline was in progress). Items that need a rendered check are marked **[render]**.

Authorities used: `DESIGN.md` (Shared components; Responsive, accessible and state rules; Brand and copy), `docs/agents/frontend.md`, React 19.2 `react-dom` source (`startHostTransition`), Next 16.3.8 docs (`error.md`, `linking-and-navigating.md`).

## Summary

- **No silently dead controls in real mode.** Every control that is disabled in real mode comes with an explicit "not available yet" notice (WP03-T17 behaviour). See "Intended disabled controls" below.
- **Two P1 defects in core flows.** (1) React 19 resets an uncontrolled `<form action={fn}>` after *every* submission, so a failed sign-in or registration clears the email the user typed. The synthetic demo hides this because its `defaultValue` is the sample email. (2) All four error boundaries call `reset()`, which in Next 16.3 re-renders without re-fetching, so "Try again" cannot recover from a server-side failure.
- **Root cause behind several P2/P3 items:** the shared primitives are thin. `Button` has no pending state, `aria-busy` or `aria-describedby`. `Select` and `ChoiceGroup` have no hint or error wiring. `Notice` signals error/success by colour only. Every surface re-implements label/hint/error by hand (often with helper text *inside* the `<label>`), and there are four separate ad-hoc Escape handlers for `<details>` popovers. Fixing the primitives first makes most of the remaining items small.
- **Mobile input semantics are mostly absent.** The only `inputMode` in the app is on the auth email field. No `enterKeyHint`, `spellCheck` or `autoCapitalize` anywhere, `useFormStatus` is never used, and no `name` is set on most client-state fields.
