# ADR-0002: Database boundaries and migration conventions

**Status:** Accepted

**Date:** 2026-08-31

## Context

UniMind's database is the durable authority for authorization, availability, provenance, jobs, usage, and audit. These rules must survive different web and worker implementations, retries, and future capacity changes. Supabase also makes schema placement part of the security boundary: an object grant controls whether a role can reach an object, while Row Level Security (RLS) controls which rows that role can access.

The schema will grow across many dependency-ordered migrations. Without one convention, identifiers, timestamps, state transitions, access grants, and historical evidence can drift in ways that TypeScript validation or UI checks cannot repair.

## Decision

### Schema and access boundaries

- Put client-reachable domain tables and narrowly scoped caller functions in `public`. Every exposed table must have RLS enabled and tested, and every table or function must have explicit least-privilege grants. A grant exposes an object; RLS filters rows. Both layers must pass.
- Put server/worker-only state and privileged helper functions in non-exposed internal schemas, beginning with `unimind_private`. Revoke broad schema and object defaults before granting a capability to an intended runtime role.
- Use `security invoker` behavior by default. An unavoidable `security definer` function belongs in an internal schema, sets an explicit safe `search_path`, verifies caller authority, has `PUBLIC` execution revoked, and receives only the required role grants.
- PostgreSQL constraints enforce durable invariants. TypeScript and request validation improve errors but never replace `not null`, foreign keys, uniqueness, state checks, or authorization below the UI.

### Identity and time

- Use UUID primary keys for externally referenced and domain entities. This permits independent creation and stable references without exposing sequence volume.
- Use generated identity keys only for internal append-only rows when measured ordering or storage benefits justify them. Do not use legacy `serial` types.
- Store instants as `timestamptz` in UTC. Every table has `created_at timestamptz not null default now()` or the transaction-equivalent default. Governed transitions also record the actor, reason, correlation ID, and transition time when applicable.

### State, history, and indexing

- Use database enums only for small vocabularies that are genuinely stable. Use named check constraints for evolving states and for legal state combinations or transitions.
- Prefer deactivation or controlled status transitions over deleting durable domain records. Accepted source versions are immutable except for controlled activation/status changes. Availability remains derived and never becomes an editable Boolean.
- Audit events, job attempts, provider calls, deletion evidence, provenance, and usage/cost entries are append-only. A correction appends a new event rather than rewriting or deleting evidence.
- Index every foreign key used for joins or deletion checks. Add authorization and filter indexes only for a named query and retain them only when its plan or benchmark supports the cost.

### Migration direction

- Create every schema, extension, table, policy, function, trigger, index, and seed change in a versioned migration generated by the pinned Supabase CLI.
- Apply forward-only changes. Repair a shared migration with a new migration; do not rewrite applied history or assume a destructive rollback is safe.
- Prove each migration through an accompanying SQL or integration test, a clean disposable reset, a populated synthetic upgrade, deterministic type generation, and the applicable grant/RLS and advisor checks.
- Use the [database migration checklist](../runbooks/database-migration-checklist.md) for the semantic review that automated convention checks cannot prove.

## Alternatives considered

- Put all objects in `public` and rely only on RLS. This makes server-only state reachable through the Data API surface and turns every grant mistake into unnecessary exposure.
- Keep authorization and invariants in TypeScript. This fails for direct database access, worker code, retries, and future adapters.
- Use mutable status/history rows and reverse migrations. This makes audit and recovery evidence unreliable and can destroy shared data during rollback.
- Add indexes and PostgreSQL enums pre-emptively. This makes writes and future state evolution more expensive without measured benefit.

## Consequences

- Migrations require more explicit constraints, grants, tests, and evidence, but failures occur at the authoritative boundary rather than leaking through an adapter.
- Some high-volume internal tables may use identity keys, but each exception needs a measured reason and remains non-exposed and append-only.
- Shared-environment rollback normally means disabling the affected capability or applying a forward repair migration.
- The SQL checker intentionally covers mechanical rules only. RLS meaning, actor authority, transition legality, query plans, and protected-gate approval still require tests and human review.
